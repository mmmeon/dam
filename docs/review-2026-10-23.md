# Review of main, 2026-10-23

*Note, 2026-10-23. A read-only review of the whole code on `main` at `d0dc9cb`, in six areas, one
reviewer each. It looks hardest at the 40 commits since `547ff8e`, which fixed
docs/review-2026-10-22.md and were live-tested (docs/live-test-2026-10-23.md). Nothing below is
fixed yet, and none of it was checked by running the app; each finding is the reviewer's, traced
through the code.*

- **CONFIRMED** means the code path was traced.
- **PLAUSIBLE** means the mechanism is there, but the outcome depends on timing, WindowServer, a
  browser or a client.
- Items from the last two reviews weren't raised again unless a fix is wrong or doesn't go far
  enough.

## Summary

35 findings, none high. Five of them come from last round's fixes:

- **Opened by last round's fixes:**
  - the system close box on picker bars, which doesn't cancel the pick;
  - a reinstalled OpenDisplay receiver refused over USB;
  - the switcher's display pages, which have no way out while DAM is active.
- **Last round's fixes don't go far enough:**
  - Fix first 4 covered the browser leaving Moonlight's displays alone, but not the other way
    round.
  - Fix first 5 doesn't reach a change made while a streaming display is being added or resized.

Six themes stand out:

- **Displays shared between servers.** Moonlight removes or resizes displays a browser is
  streaming, and keeps acting on a display ID after the display has gone.
- **Who may pair and with what name.** Any `.local` name passes the Host check, so DNS
  rebinding from the LAN is open. Browsers with an old Secure cookie loop through pairing.
- **Links mixing with real sessions.** A detected session that joins a link's session takes on the
  link's settings, and a link can adopt one of the Mac's monitors.
- **DAM undoes its own changes, still.** This happens while a streaming display is placed, after
  wake, and when identical monitors' names swap.
- **Touch Bar exits.** These are the switcher's pages, the picker close box, and the switcher
  coming back after it was closed.
- **What sessions learn.** A session can learn another session's output, or "extend" when another
  session's display took main.

## Fix first

1. **Displays shared between Moonlight and the browser.**
   - **Moonlight removes or resizes a display a browser is streaming** (CONFIRMED, found in two
     areas; `MoonlightHost.swift:708-716, 739-751`; `WebStream.swift` `serve`).
     - **The gap:** `letGo` and `shared` count only Moonlight sessions.
     - **How it happens:**
       - The browser is offered Moonlight's "New Display" displays, and a link with no app picks
         `apps.first`.
       - A Moonlight cancel, a relaunch or hosting stopping removes the display, and the
         browser's stream dies.
       - A resume at another size resizes it under the viewer.
       - A display the browser handed over is cut off the same way.
     - **Fix:** give MoonlightHost an `othersStream`/`handOver` pair wired to the web server.
   - **Moonlight never forgets a display that went** (mechanism CONFIRMED, ID reuse PLAUSIBLE;
     `MoonlightHost.swift:695-749`, `AppDelegate.swift:121-125`).
     - **The gap:** `onStreamingDisplayGone` doesn't tell Moonlight, so a launch keeps `displayID`
       and `ownsDisplay`.
     - **How it happens:** a later display gets the same ID, because the serial comes from the
       slot. The device's next cancel then removes it, or its resume resizes it.
     - **Fix:** add `MoonlightHost.displayGone(id)`.
2. **Who may pair.**
   - **DNS rebinding through local names** (PLAUSIBLE; `WebStream.swift:469, 478`).
     - **The gap:** `namesThisMac` accepts any single-label name or any name under `.local`,
       `.lan`, `.home` and the other local suffixes.
     - **How it happens:**
       - A LAN host answers mDNS for `evil.local` with its own address, then the Mac's.
       - The prompt then names the victim's own browser, and the code shows in that browser.
       - The user types it, and the cookie lands on the attacker's origin.
     - **Fix:** accept only the Mac's LocalHostName (with local suffixes), `localhost`,
       certificate names and the user's "Also Reachable As" names.
   - **Browsers paired over HTTPS before the update loop over HTTP** (CONFIRMED in code;
     `WebStream.swift:620-621, 671-674, 2096-2108`).
     - **The gap:** the old Secure `dam_watch` blocks the HTTP cookie.
     - **How it happens:**
       - The page sees "paired", `/apps.json` answers 401, and it pairs again.
       - Each round leaves a device and brings up a prompt.
       - The back-off doesn't apply, because each prompt was answered.
     - **Fix:** when HTTPS authenticates with the legacy name, re-issue the cookie as
       `__Secure-dam_watch` and expire the old one.
     - This goes past the "let them expire" decision.
3. **Links mixing with real sessions.**
   - **A detected or command start that joins a link's session takes on the link's settings**
     (CONFIRMED; `RemoteSessions.swift:467-495`).
     - **How it happens:**
       - It runs with the link's display and output, and with blackout off.
       - When the app ends, the count falls back to the link's 1, so the session stays on.
     - **Fix:** set it up again from the joiner's request and profile, or keep link sessions
       apart.
   - **A link can adopt a physical display** (CONFIRMED path; `RemoteSessions.swift:530-546,
     782-806, 659`).
     - **How it happens:**
       - `dam://session/start?app=retina&display=adopt&placement=mirror` matches the built-in.
       - `app=lg&display=adopt&placement=main` makes an external monitor main.
       - Ending the session puts neither back.
     - **Fix:** refuse `display=adopt` from links, or adopt only non-physical displays, and put
       back an adopted display's main and mirroring at the end.
4. **DAM still undoes changes made through DAM.**
   - **During a streaming add or resize** (CONFIRMED; `VideoManager+StreamingDisplay.swift:564,
     689, 749-767, 854-875`).
     - **The gap:** the placement commits a local `before` that `keepUserMode`/`keepUserOrigins`
       don't reach. Its 5 s settle then reasserts it.
     - **Fix:** keep the in-flight `before` stored and folded, or hold `setMode`/`arrange` while a
       change is in flight.
   - **The wake restore** (PLAUSIBLE; `VideoManager.swift:310-353`).
     - **The gap:** it folds into nothing.
     - **How it happens:** an iPad or TV that gets an anchor after wake keeps the wrong post-wake
       mode for 30 s and reasserts it over both restore passes.
     - **Fix:** fold each restored mode with `keepUserMode`.
5. **Identical monitors' names swap** (CONFIRMED; `VideoManager.swift:1305-1320, 1439-1445`).
   - **The gap:** `distinctNames` ranks by serial from scratch on every merge.
   - **How it happens:**
     - Plugging in a second "DELL" with a lower serial renames the first to "DELL (2)".
     - Its anchor, rotation stand-in, saved rotation, nickname and hidden setting then follow the
       wrong monitor.
   - **Fix:** keep each online display's name while it stays connected, and give only newcomers
     the next suffix.
6. **Touch Bar exits.**
   - **The switcher's display pages have no way out while DAM is active** (CONFIRMED;
     `ControlStripPresenter.swift:457-500`). The resolutions page has no ◀ and no close.
     a5e151b added the close button only to the main and audio bars.
   - **The system close box now shows on picker bars, and tapping it doesn't cancel the pick**
     (PLAUSIBLE; this came from 7ba58a8; `ControlStripPresenter.swift:73-87`,
     `ChoicePicker.swift:159-164, 224-231`).
     - **How it happens:** `pickTimer` still fires, so the output, mirror, main display or
       resolution changes after the user closed the picker.
     - **Fix:** keep the close box off for picker and quick-connect bars, or treat their bar
       vanishing as Cancel.
   - **A pending change brings the switcher back after it was closed** (CONFIRMED;
     `ControlStripPresenter.swift:804-850`, ArrangeTouchBar `end()`).
     - **The gap:** Main, Mirror, Optimize and Arrange completions call `openModal()` or
       `showDisplayPage` without checking that the switcher is still open.
     - **Fix:** keep a generation, bumped on close.
7. **A reinstalled OpenDisplay receiver can't connect over USB** (CONFIRMED path; it came from
   7397d51; `OpenDisplaySender.swift:337-360, 598-604, 751-755`).
   - **How it happens:** the cable's serial still maps to the old install ID, so every hello
     mismatches and the receiver is dialed every 5 s forever.
   - **Fix:** check the ID only over TCP. On a cable, update `usbIDs[serial]`.
8. **The last change on screen can be dropped** (PLAUSIBLE; it was there before last round's
   fixes; `MoonlightScreenCapture.swift:302, 475-486`).
   - **How it happens:**
     - FramePacer drops a final frame that comes less than 0.75 frame times after the one
       before.
     - A still screen sends nothing more.
     - Moonlight, the browser and OpenDisplay then show the picture before last until the screen
       changes.
   - **Fix:** a trailing-edge delivery of the dropped frame.
9. **What sessions learn.**
   - **Two sessions both switching the output** (CONFIRMED; `RemoteSessions.swift:661-666,
     709-713`).
     - **How it happens:** when the later one ends first, the output stays at its choice, and the
       earlier one saves that output in its profile.
     - **Fix:** switch back to the remaining owner's output, or update its `outputAfterStart`.
   - **"Extend" learned when another session's display took main** (CONFIRMED path;
     `RemoteSessions.swift:693-696, 826-837`).
     - **How it happens:** Parsec and RustDesk both default to main, so overlapping sessions save
       Extend.
     - **Fix:** learn a placement only from a change made through DAM to that display.

## Worth fixing

### Moonlight host

- **One unauthenticated request breaks a pairing in progress** (CONFIRMED;
  `MoonlightHost.swift:548-590, 785-813`).
  - **How it happens:** a `/pair?clientchallenge=` out of order, or an `/unpair`, from any
    address clears `pairing` while the PIN prompt is up. It can be repeated on every try.
  - **Fix:** answer pairing steps only from `pairingAddress`.
- **`PairingPromptLimits` isn't shared between the servers** (CONFIRMED, found in two areas;
  `MoonlightHost.swift:295, 1160-1199`, `WebStreamAccess.swift:197`).
  - **The gap:** each server makes its own, so the cap is 6 prompts a minute, not the 3 its
    comment says.
  - **IPv6:** a host can rotate addresses in its /64 and escape the per-address back-off.
  - **Fix:** inject one instance, key IPv6 by /64, and double the global wait.

### Media

- **An oversized keyframe is asked for again, but each retry is just as oversized**
  (PLAUSIBLE; `MoonlightStream.swift:1051-1056`, `MoonlightProtocol.swift:222-225, 405-409`,
  `MoonlightVideoEncoder.swift:481-486`).
  - **How it happens:** above about 120 Mbit/s (88 with 1024-byte packets), `DataRateLimits`
    allows keyframes the packetizer can't send. With adaptive bitrate off, the picture stays
    frozen.
  - **Fix:** cap the byte budget at the packetizer's largest frame.
- **Spoofed CONNECTs still fill the control stream** (CONFIRMED in vendored ENet;
  `MoonlightStream.swift:687-688`, `Vendor/enet/protocol.c:310-332`).
  - **How it happens:**
    - 32 CONNECTs from 16 forged addresses take every peer.
    - Two forged with the client's address use up its quota.
  - **Fix:** drop CONNECTs with the wrong token in `host->intercept`, before a peer is allocated.

### Browser stream

- **Host check on the main queue** (PLAUSIBLE; `WebStream.swift:480, 620`,
  `WebStreamAccess.swift:461-468`).
  - **The gap:** `ProcessInfo.processInfo.hostName` can block on DNS. It runs for every dotted,
    non-local Host, tokens included.
  - **Fix:** cache the names, or check the token first.
- **The owned display is kept after a device is forgotten mid-turn** (CONFIRMED, narrow;
  `WebStream.swift:739, 744, 796-803`).
  - **Fix:** release on every early return in `serve`.
- **A turn resizes the display for other browser viewers** (CONFIRMED path;
  `WebStream.swift:791-792`).
  - **The gap:** `othersStream` asks only Moonlight.

### Displays

- **A stand-in's swap** (PLAUSIBLE; `VideoManager+Rotation.swift:183-214`).
  - **What goes wrong:**
    - It replaces `streamingSettle` with the live layout.
    - It commits without checking the in-flight flags.
    - `endPresentation` during a streaming add can leave the covered screen parked at the right.
- **DAM's own displays listed as physical while they go** (CONFIRMED path;
  `VideoManager.swift:1432-1452`).
  - **The gap:** `isAnchorDisplay` filters only product `0x1234`.
  - **What is listed:** the bootstrap stand-in (`0x1235`) and a removed streaming display are
    listed, offered to Moonlight and the browser, and named in `distinctNames`.
- **A commit that times out and then fails is kept** (PLAUSIBLE; `VideoManager.swift:1013-1034`
  with `:751, :1295`, `VideoManager+Arrangement.swift:105`).
  - **Fix:** run the undo on a late failure.

### OpenDisplay and sessions

- **OpenDisplay still takes up a crash's session once it has run past a day** (CONFIRMED path;
  `SessionDetectors.swift:170-181, 360-364, 462-467`).
  - **The gap:** the log has only times of day, so every tail line dates within 24 h.
  - **Fix:** a launch line in the fork's log, full dates, or stop at the first time that goes
    backwards.
- **"Light This Mac's Screens" tooltip contradicts what it does** (CONFIRMED;
  `MenuBuilder.swift:155` vs `RemoteSessions.swift:731-743`).

### App and UI

- **Focus is handed back after the user moved into a DAM window** (CONFIRMED path;
  `AppDelegate.swift:356-380`, `HUD.swift:682-685`).
  - **The gap:** a watch that gives up leaves `switcherPreviousApp` set, and a later close
    activates that stale app.
- **Another DAM bar over the switcher reads as it closing** (PLAUSIBLE;
  `ControlStripPresenter.swift:700-713`).
- **`switcherClosed`'s alert guard never fires** (CONFIRMED; `AppDelegate.swift:376-380`).
  - **The gap:** the watch timer doesn't tick during a modal alert, so the comment's promise
    doesn't hold.
- **Launch at login shows on for an item turned off in System Settings** (PLAUSIBLE;
  `VisibilityPreferences.swift:221-226`, `SettingsWindowController.swift:318-349`).
  - **The gap:** `.requiresApproval` reads as on, and the state isn't re-read when Settings
    comes back.
- **The Switcher hotkey re-opens the menu** when pressed to dismiss it (PLAUSIBLE;
  `AppDelegate.swift:366-371`, `GlobalHotkey.swift:59`).
- **A picker with nothing current speaks entry 0, but the pause doesn't pick it** (CONFIRMED;
  `ChoicePicker.swift:96-100, 152-163`).
  - **The gap:** the first press then skips to entry 1.
- **Accessibility:**
  - Hotkeys' "Reset" buttons have no context, and nicknames have no label
    (`SettingsWindowController.swift:449-461, 1628-1640`).
  - The recorder's value is read as symbols.
- **Audio devices hidden by the old virtual rule stay hidden** (`AudioManager.swift`): PCI, AVB
  and unknown transports were already "seen". This needs a one-time migration.
