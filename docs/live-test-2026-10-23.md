# Live test of review/integration-3, 2026-10-23

*Note. Release build of `review/integration-3` (the fixes for docs/review-2026-10-22.md),
installed into /Applications and driven from the shell on this Mac: Moonlight over 127.0.0.1
with tools/streamtest, the AirPlay TV "tv" connected and disconnected through DAM's menu with
System Events, curl for the browser stream. No problems found in the fixes.*

## Passed

- **Remote sessions.** `tools/sessiontest/sessiontest run`: 58 passed, 0 failed, 1 skipped
  (user-main needs a second physical display). Logs in /tmp/dam-sessiontest/20261023-091726.
- **Moonlight stream, with a resize to 1280×720.**
  - Stream: no lost blocks or refused packets, and Moonlight's log has 0 "reference frames"
    errors.
  - Latency and frame rate: median delay 31 ms, then 43 ms after the resize; 47.7 fps on
    average.
  - Same as `main`: a build of `main` run the same way gave 47.8 fps and 30/42 ms, so the
    pacer changes cost nothing here. The frame rate is this Mac's capture limit.
- **A stream turned 180°**, with a resize: no mirroring, resized in place. (streamtest starts the
  display already turned, so turning 0°↔180° during a stream wasn't tried.)
- **The TV joining mid-stream.**
  - About 2 s after joining, WindowServer mirrored the streaming display onto the TV, and DAM
    freed it about 1 s later.
  - The time-code windows stayed on their displays.
- **A resolution set through DAM is kept (Fix first 5).**
  - The streaming display was set to 1280×720 from the menu.
  - When the TV joined, WindowServer set it back to 1920×1080, and DAM put the user's 1280×720
    back, not the size it was made at.
- **A move within 45 s of the TV joining is kept.** "Position → Below lenovo" held past the 45 s
  window instead of being moved back.
- **The TV leaving mid-stream.**
  - WindowServer applied a layout saved earlier, and DAM put the streaming display's mode back
    within a second.
  - The window on the streaming display stayed on it.
- **Browser pairing refusals**, all checked with curl:
  - GET `/pair/begin` and a POST elsewhere: 405.
  - A foreign Origin, or `Sec-Fetch-Site: cross-site`: 403.
  - A rebinding Host: 403 "Open this page by the Mac's name or address."
  - A cookie under a foreign Host: 401.
  - A bad QR key: 403.
- **Browser pairing back-off.** A same-origin POST brought up the alert. After Cancel, asking
  again answered "Try again in 29 seconds." and showed no alert.
- **A browser display handed to Moonlight (Fix first 4).**
  - Moonlight launched the display a browser stream had made (This Mac's link, via curl).
  - Closing the browser side left the display up and Moonlight streaming.
  - `Moonlight quit` removed the display.
- **An existing pairing still works.** The iPhone's tab reconnected through the new Host and
  cookie checks after the reinstall.

## Not tested live

- **HDR10 colours, oversized keyframes, the audio drain:** HDR10 needs an HDR client, oversized
  keyframes need ones over 4 MB, and the audio drain needs a lossy link.
- **The Switcher hotkey's menu (Fix first 8):** this Mac (MacBookPro14,2) has a Touch Bar, so the
  hotkey takes the Touch Bar path, not the menu.
- **OpenDisplay:**
  - an ID mismatch, and a crash and relaunch;
  - with tools/odreceiver, the test receiver must be turned on in Settings, which wasn't opened.
- **Parsec or Chrome Remote Desktop quitting mid-session:** there was no remote client.
- **Wake while streaming, and a stand-in on an anchored screen:** wake needs the Mac to sleep,
  and the stand-in needs an anchored TV or iPad.
- **Other UI:** recording ⌘Q, VoiceOver, dead keys, two identical monitors, and launch at login
  while it waits for approval.

## Worth knowing

- **Two "tv" items in DAM's menu.** When the TV is the sound output, "tv" appears twice: under
  Audio Output and under AirPlay Display. Scripts must pick the AirPlay one, the one with a
  submenu.
- **Driving the menu with System Events.** Do each step (opening the menu, an item, a submenu
  item) as its own `osascript` call. Done in one script, the menu is often gone by the next step.
- **Escape quits the time-code window.** Sending Escape to close a menu that isn't open reaches
  tools/latency's window instead, and it quits.
