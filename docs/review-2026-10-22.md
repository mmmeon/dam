# Review of main, 2026-10-22

*Note, 2026-10-23. A read-only review of the whole code on `main` at `fcb0bf5`, in six areas, one
reviewer each, at high effort. Nothing below is fixed yet, and none of it was checked by running
the app: each finding is the reviewer's, traced through the code. CONFIRMED means the code path was
traced; PLAUSIBLE means the mechanism is there but the outcome depends on timing, WindowServer or a
client that couldn't be watched. Items left open by docs/review-2026-10-21.md were not raised
again unless a finding goes past them.*

## Summary

56 findings, none high. Six themes stand out:

- **Prompts on demand.** Anyone in reach can make both servers' pairing prompts come back as
  often as they like.
- **Ports and slots held by strangers.** A failed stream start leaks a Moonlight slot's control
  port for good, and four unauthenticated packets fill the control stream's peers.
- **Displays changed under others.** The browser stream removes or resizes displays Moonlight is
  streaming.
- **DAM undoes changes made through DAM.** Its kept layouts aren't updated by its own resolution
  and arrangement changes.
- **Sessions learn failures.** Remote-session profiles save what failed as the user's choice.
- **Pacing gaps.** Moonlight's video pacer bursts after parity and leaves the last frames unsent.

Found sound, area by area:

- **Moonlight host:** pairing (steps can't repeat; HTTPS admits only the paired DER), parsing of
  HTTP/RTSP/SDP/control/input, sessions and slots, the RTSP address check, input injection's
  release and clamping, `MoonlightListenerRestarts`.
- **Media:** the packetizer and FEC arithmetic, GCM/CBC nonces and IVs, the encoder's threading and
  PTS, `H264OneReference`, the keyframe throttle and bitrate governor.
- **Browser stream:** every MP4Fragmenter box, the page's FragmentReader, viewer and session
  threading, token randomness and comparison, cookie flags, certificate parsing and key file
  permissions, the page's use of `textContent` only.
- **Displays:** mirror plans, main-display rollback, arrangement restore math, DisplayLayout, every
  in-flight flag being cleared, LocalBlackout, ScreenMirroringPanel, AirPlayQuickConnect, threading
  of CG callbacks.
- **OpenDisplay, control, sessions:** the control socket (0600, peer uid, JSON only, nothing
  reaches a shell), OpenDisplay framing and hello bounds, teardown order, log following through
  rotation and truncation.
- **App and UI:** launch and quit ordering, weak captures, menu state, hotkey pause/resume
  balance, Settings controls applying, UserDefaults keys, the icon's animation settling.

## Fix first

1. **Pairing prompts on demand.**
   - Browser stream (CONFIRMED; `WebStream.swift:507, 536-554`, `WebStreamAccess.swift:196-204`,
     `AppDelegate.swift:745-764`). `/pair/begin` is a GET with no Origin or `Sec-Fetch-Site`
     check, and `begin()` takes a new request as soon as the last is declined. A LAN host looping
     it, or a page the Mac's user opens (`<img src="http://localhost:47995/pair/begin">`), brings
     the app-modal alert back after every Cancel, each time activating DAM and speaking. Back off
     per address after a decline, require POST and same origin, cap prompts a minute.
   - Moonlight (CONFIRMED path; `MoonlightHost.swift:772`, `AppDelegate.swift:767-790`). The PIN
     prompt is queued with `RunLoop.main.perform(inModes: [.default])` and never checks its pairing
     is still current; `pairingAbandoned` only aborts an alert on screen. Repeated `getservercert`
     and hang-up while a menu is open stacks stale alerts that appear one after another once it
     closes; outside a menu each round trip steals focus. Check the pairing before showing, and
     rate-limit.
2. **A failed ANNOUNCE leaks the slot's control port** (CONFIRMED path; `MoonlightStream.swift:852-855`
   with `:604-667`). If `MoonlightAudioSender.init` throws after `MoonlightControlServer.init` ran
   `enet_host_create`, the ENet host is never destroyed (no `deinit`; only `start()`'s thread
   destroys it). Every later ANNOUNCE on that slot fails at the ENet bind, until DAM quits. Makes the
   "re-ANNOUNCE may fail to bind" item of the last review permanent when it happens. Destroy the
   host when `start()` never ran.
3. **Four packets fill the control stream** (CONFIRMED in vendored ENet; `MoonlightStream.swift:640`).
   The ENet host has 4 peers and no per-address limit; a CONNECT never acknowledged holds a peer for
   ENet's timeout (5–30 s) without `handle()` seeing it. Any LAN host spraying CONNECTs at 47999,
   48099… makes real clients fail with "control stream connection failed". Raise the peer count and
   set `enet_host_set_duplicate_peers` to 1–2.
4. **The browser stream removes or resizes displays Moonlight streams** (CONFIRMED;
   `WebStream.swift:581-584, 646-656, 720-723`, `AppDelegate.swift:290-299`). A display made for a
   browser is listed to Moonlight; a client can launch it (`ownsDisplay` false). When the tab
   closes, on `stop()`, or on a certificate import (`stopAll()`), the browser stream removes it and
   Moonlight's stream dies. A second viewer turned the other way resizes it under Moonlight, which
   itself refuses that ("A display another device is streaming keeps its size").
5. **DAM reverts its own changes** (CONFIRMED). DAM keeps layouts to put back: `StreamingDisplay.start`,
   `streamingSettle` (5 s), `framesBeforeSetChange` (45 s), `streamingArrangement`,
   `virtualAnchorArrangements` (30 s). Changes made through DAM don't reach all of them.
   - `setMode` (menu, picker, Touch Bar) never updates `StreamingDisplay.start`
     (`VideoManager+StreamingDisplay.swift:708, 330-338`; `VideoManager.swift:1151`): a display
     made at 1920×1080 and set to 2560×1440 turns to 1080×1920; a 180° turn sets 1920×1080 back;
     a TV or iPad joining within 45 s puts `start` back.
   - `arrange()` (Arrange window, Position menu, Touch Bar, `extend(member:to:)`) doesn't update
     `streamingSettle` or `framesBeforeSetChange` (`VideoManager+Arrangement.swift:80-117`): a drop
     within 5 s of a streaming change, or a streaming display dragged within 45 s of any display
     joining or leaving, is moved back.
   - `setMode` doesn't update `streamingSettle` or `streamingArrangement` (`VideoManager.swift:1160-1163`):
     the built-in set to another resolution during a stream goes back to its pre-stream mode when the
     last streaming display is removed.
   - `resizeStreamingDisplay` and rotation don't update `virtualAnchorArrangements[...].modes`
     (`VideoManager+VirtualAnchor.swift:1425`): a client coming back at another size within an
     anchor's 30 s settle sees its display flip between sizes, ending wrong.
6. **Remote-session profiles learn failures** (CONFIRMED; `RemoteSessions.swift:598-620`). `learn(from:)`
   compares the end state with what was asked, not what was achieved. A failed `setMainDisplay`
   saves `extend` for good; an output that wasn't connected saves the speakers; `--audio X` that
   failed is kept although request options never are. The size check has the same shape (PLAUSIBLE).
   `testMissingOutputAndFailedPlacingAreWarnings` never ends its session.
7. **Sessions nothing can end, and URLs that end or join them** (CONFIRMED).
   - `followsApp` is true for any request or profile that adopts (`RemoteSessions.swift:451`), and the
     menu then shows only "Ends when X stops" (`MenuBuilder.swift:266`). `dam://session/start?app=foo&display=adopt&placement=mirror`
     for an app no detector knows stays on with no End; with `blackout=yes` and no display found,
     every physical screen stays black until `DAM session end` or DAM is killed.
   - `dam://session/end?app=sunshine&all=yes` from any page or sandboxed app ends a live session;
     `dam://session/start?app=rustdesk` during a detected one joins it, so the real close leaves the
     display, output and blackout on (`AppDelegate.swift:272-280`, `ControlSocket.swift:553-568`).
     Goes past the last review's "web pages can start sessions".
8. **The Switcher hotkey's menu blocks the main queue** (CONFIRMED; `GlobalHotkey.swift:69`,
   `AppDelegate.swift:343-348`). Without the Touch Bar it calls `statusItem.button?.performClick`
   inside a `DispatchQueue.main.async` block, and the menu tracks modally there: OpenDisplay's
   timers, Moonlight's and the browser stream's listeners and connections and the Bonjour browsers
   stall until it closes. Use `RunLoop.main.perform`, as the PIN alert does.
9. **Moonlight's video pacer** (CONFIRMED).
   - Parity time isn't added to the pace (`MoonlightStream.swift:448-464`): due times are
     `began + bytes × nsPerByte`, so after each FEC block's parity (about 6 ms at -O for 144 packets)
     its parity and the next block's first packets go back to back, about 90 KB at line rate per
     block of a 600 KB keyframe. Move `began` on by the time spent, or cap the credit. Untested.
   - Frames skipped while the sender is behind are never encoded (`MoonlightStream.swift:1008-1011,
     1072-1081`): when the screen goes still after a burst, only the 0.5 s repeater sends the last
     picture, so the client is 0.5–1 s stale after big changes. Encode `lastFrame` when the sender
     drains after skipping.
10. **Hotkey recorder takes app shortcuts** (CONFIRMED; `KeyRecorderView.swift:120-134`). No
    `performKeyEquivalent`, so ⌘Q quits DAM, ⌘H, ⌥⌘H, ⌘W act, and none can be recorded.
11. **Two monitors of one model are one** (CONFIRMED; `VideoManager.swift:1324` makes an external's
    `id` its name). On the Touch Bar (`ControlStripPresenter.swift:329, 353-362, 416-419`) the second
    monitor's button and resolution bar act on the first; on the Devices tab
    (`SettingsWindowController.swift:349-357`) both rows toggle and nickname the same name.
12. **Accessibility** (CONFIRMED). `KeyRecorderView` has no accessibility element, so VoiceOver skips
    the Hotkeys tab; the refresh-rate checkboxes have empty titles (`SettingsWindowController.swift:1562`);
    the status item has no label or tooltip (`AppDelegate.swift:283-286`).

## Worth fixing

### Browser stream

- **Paired over HTTPS, can't pair over HTTP** (PLAUSIBLE; `WebStream.swift:557-560, 494, 514`).
  `dam_watch` is `Secure` over HTTPS and not over HTTP; browsers drop a non-Secure cookie while a
  Secure one of that name exists. An iPad paired over HTTPS that scans a QR code (always HTTP)
  pairs again and again, each leaving an unusable device. Use a `__Secure-` name for HTTPS.
- **No Host check** (CONFIRMED missing; `WebStream.swift:477-534`): DNS rebinding makes a page
  same-origin; if the user types its code, the cookie and `/stream.mp4` are the page's.
- **A display kept after a failed serve** (CONFIRMED; `WebStream.swift:608, 638-640, 657-674`): a 503
  after `makeDisplay` leaves `ownedDisplay` with no session (`WebStreamTests.swift:684-685` shows it);
  it's never cleared when the display goes, and IDs come back.
- **Turning the phone can remove its display** (PLAUSIBLE; `WebStream.swift:646-656, 909-915, 717-723`):
  a resize slower than the old session's 3 s grace lets `ended()` remove the display being resized.
- **Reach checked after admission** (CONFIRMED; `MoonlightHost.swift:1080-1096`, `WebStream.swift:380-382, 478`):
  with This Mac Only, a LAN host can keep all 64 connection slots full. Check reach in `accept`.
- **No cap on sessions** (CONFIRMED; `WebStream.swift:660-679`): 16 connections with distinct bitrates
  make 16 captures and encoders.
- **QR keys pair with pairing off** (CONFIRMED; `WebStream.swift:485-496`, `SettingsWindowController.swift:579`).
- **A typed code's request can be replaced** (CONFIRMED, narrow; `WebStreamAccess.swift:196-204`) before
  its browser collects the cookie.

### Moonlight host

- **The main queue waits on encoder measuring** (CONFIRMED; `MoonlightHost.swift:517, 613`):
  `/serverinfo` and `/launch` read `VideoCodec.support`/`performance` while `measureEncoders()` may be
  initialising them, about 1 s after a macOS update or first run.
- **IPv6 clients fail late** (PLAUSIBLE; `MoonlightHost.swift:638`, `MoonlightStream.swift:127, 640`): the
  listeners are dual-stack, the stream's sockets IPv4, and `sessionUrl0` writes an IPv6 address without
  brackets; the stream ends after 10 s with "Moonlight never asked for video". Refuse IPv6 at /launch
  with a message, or support it.

### Media

- **A slow capture start kills every capture** (PLAUSIBLE; `MoonlightScreenCapture.swift:134-138`):
  `SCShareableContent` taking over 2 s SIGKILLs replayd, ending other Moonlight, browser and
  OpenDisplay streams. Check for live captures first, or wait longer.
- **HDR10 tags set after rendering** (PLAUSIBLE; `MoonlightScreenCapture.swift:379-385`): if Core Image
  takes the matrix from the buffer's attachments, saturated colours shift. Tag before rendering and test
  a saturated colour.
- **Audio backlog never drains** (CONFIRMED; `MoonlightStream.swift:515, 575-584`): the pacer sends one
  packet per fire and ignores coalesced fires; once at `maxWaiting` (8 packets, 80 ms at 10 ms packets,
  not the 40 ms the doc says) each missed tick or clock drift drops a packet.
- **A requested keyframe too large to send isn't asked for again** (PLAUSIBLE freeze;
  `MoonlightStream.swift:439-444`, `MoonlightProtocol.swift:367, 258`): the retry is `.covered` and
  `frameIndex` doesn't advance, so the client waits for an IDR that never comes. Needs a keyframe over
  about 4–5.7 MB.
- **A joining stream can get an older frame** (CONFIRMED, narrow; `MoonlightScreenCapture.swift:569-576`).
- **0°↔180° and 90°↔270° turns** pass a frame or two the old way up (CONFIRMED;
  `MoonlightScreenCapture.swift:269-277`).

### Displays

- **Stand-in on an anchored screen** (move CONFIRMED, end layout PLAUSIBLE;
  `VideoManager+Rotation.swift:149-156`, `VideoManager+StreamingDisplay.swift:633`): the anchor is
  never moved, so the stand-in lands on top of it and the pointer fence warps the pointer back.
- **Wake restores old modes onto streaming displays** (PLAUSIBLE; `VideoManager.swift:300-337`), and
  its commits can race a streaming add.
- **A rotation undone through macOS stays saved** (CONFIRMED; `VideoManager+Rotation.swift:56-57, 81-104`):
  the monitor is turned again on every launch.
- **The 10 s commit timeout** (PLAUSIBLE; `VideoManager.swift:900-924, 883-893, 712-713`) is about what
  mirroring changes took on the test Mac; a timed-out dissolve abandons the mirror.
- **Releasing an anchor** lists it as a physical "DAM" display during the teardown commit (CONFIRMED;
  `VideoManager+VirtualAnchor.swift:783`, `VideoManager.swift:1307-1317`).
- **A display the system ended** doesn't clear `streamingDisplayIsMainByChoice` (CONFIRMED;
  `VideoManager+StreamingDisplay.swift:784-796`).
- **A queued removal by slot index** can remove a newer display (PLAUSIBLE;
  `VideoManager+StreamingDisplay.swift:435-441, 585-586`). Store the display in the request.
- **A failed mirror is still kept** in the layouts to put back (PLAUSIBLE; `VideoManager.swift:715-722, 747-765`).

### OpenDisplay and sessions

- **Another session's restore is learned** (CONFIRMED; `RemoteSessions.swift:617-619, 580-583`):
  B ends and puts the output back; A, ending later, saves that as its own.
- **A hello with another ID is still streamed to** (CONFIRMED path; `OpenDisplaySender.swift:336-347`):
  after a network change, `lastAddress` can be another receiver, which gets the screen and the pointer.
  End the session when the hello's ID doesn't match.
- **Detectors without an `isRunning` check** (PLAUSIBLE; `SessionDetectors.swift:581-588, 611`): Parsec,
  Chrome Remote Desktop and added apps crashing mid-session leave the session on.
- **OpenDisplay revives an old session from its log** (PLAUSIBLE; `SessionDetectors.swift:333-335, 592-597`)
  after a crash and relaunch, and as a followsApp session it can't be ended from the menu.
- **Quitting while a session starts** keeps `outputBeforeSessions` (CONFIRMED;
  `RemoteSessions.swift:570-573, 653-655, 371-376`), and the next launch forces that output back.

### App and UI

- **Hidden displays leave Moonlight and the browser** (CONFIRMED; `AppDelegate.swift:290-299`): the
  Devices tab says only "menu bar and Touch Bar".
- **Pickers jump to the first entry** when the current choice isn't listed (CONFIRMED;
  `AudioOutputPicker.swift:40-45`, `ResolutionPicker.swift:45-49`, `MainDisplayPicker.swift:33`).
- **A pick's error is spoken over** by the choice's name (CONFIRMED; `ChoicePicker.swift:159-163`).
- **Launch at login ignores failures** (CONFIRMED; `SettingsWindowController.swift:309-311`,
  `VisibilityPreferences.swift:221-231`): a throwing `register()` leaves the box checked;
  `.requiresApproval` shows unchecked.
- **Key names** (CONFIRMED; `HotkeyPreference.swift:119-142`): `OptionBits(kUCKeyTranslateNoDeadKeysBit)`
  is 0, so dead keys show as "(33)"; F-keys, arrows, Space and Return have no names.
- **PCI, AVB and unknown audio transports count as virtual** (PLAUSIBLE; `AudioManager.swift:250-268`)
  and are hidden by default.
- **The Switcher shows nothing** while a DAM window is open behind another app (PLAUSIBLE;
  `AppDelegate.swift:343-349`, `HUD.swift:671-679`): `openSwitcher` doesn't activate DAM.
- **The Devices tab rebuilt while a nickname is typed** (PLAUSIBLE; `SettingsWindowController.swift:388-397, 403`)
  when an AirPlay or audio device comes or goes.
